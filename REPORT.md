## 1. Design choices
Pure C++17 core library (`src/core`) with no I/O or UI; a thin C++ transport layer (`src/app`) exposes JSON over a loopback HTTP server and serves a single-file HTML/JS UI. Rationale: the brief allows any frontend, but all computation, parsing and concurrency must be C++; a browser UI gives usable 3-D/2-D rendering with zero third-party dependencies, and `Launch.exe` simply starts the server and opens the default browser (statically linked, WinMain, no console). The UI never computes results; the benchmark runs on a C++ thread, polled for progress, with an atomic cancel flag that discards partial results. Errors are returned as `{"error": "..."}` with line numbers and a remedy, and shown in a banner.

## 2. Thermal FEA verification (Task C)
Weak form for -(kA T')' = qA with linear shape functions gives Ke = (kA/h)[[1,-1],[-1,1]] and fe = (qAh/2)[1,1]. Global assembly is symmetric tridiagonal; both Dirichlet values are imposed by moving the known column to the RHS and replacing the boundary row (symmetry kept), then a Thomas solve. Units: x m, T C (K differences identical), k W/(m K), q W/m^3, A m^2 (A cancels in this problem).
Results (results/fea_convergence.csv): max error at element midpoints using FE interpolation: N=10: 1.25 C; N=20: 0.3125 C; N=40: 0.078125 C; N=80: 0.01953125 C. Observed order 2.000. This matches the analytic interpolation error of a linear interpolant of a quadratic, |f''|h^2/8 = (q/2k)h^2/4 = 125 h^2 (unit test asserts it to 1e-9). Nodal errors are ~1e-13 to 1e-12 C: for 1-D linear FEM with constant coefficients the nodal solution is exact (superconvergence), so reporting nodes alone would hide the discretisation error - hence the midpoint metric. Plots: results/fea_temperature_vs_x.png, fea_convergence.png; CSV: fea_solution.csv.
**Debugging insight:** a first draft subtracted the boundary couplings with fixed indices (`f[1]`, `f[n-1]`), which is wrong for n=1 (both boundary nodes are adjacent); the single-element test (n=1 must return [100,20]) exists because of that, and the code now guards it. Also, a quick check that nodal errors were ~1e-13 initially looked "too good"; reasoning through superconvergence explained it, and the midpoint metric was adopted to expose the real O(h^2) error.

## 3. CAD / ANSYS-style visualisation (Task B)
C++ parsers (src/core/formats.cpp) validate and return structured data: ASCII STL (keyword grammar, finite coordinates, bounding box, binary detection, empty-solid message) and CSV (exact header, 5 columns, integer unique ids, finite numbers, BOM/CRLF tolerant, empty/header-only messages). The UI shows STL triangles (painter-sorted, rotate/pan/zoom/fit) and the CSV as a 3-D coloured point cloud with legend (deg C, min/max), and click-to-inspect (id, xyz in m, T in deg C). Samples: data/ with provenance; the CSV is synthetic and labelled so. Not done: mesh-to-result registration (not required), STL normals/lighting (flat shading approximated), binary STL.
Tested sizes: unit tests + sample files only on the authoring machine; **the 100 MB cap is enforced but large-file timing was not measured** [CANDIDATE: measure on your machine and fill in].

## 4. Multicore performance (Task D)
Batch: reproducible generator (mt19937_64, seed 42, own mapping to k in [1,100], q in [1e3,1e5]); identical solver code serial vs parallel; bounded pool of `std::thread` workers pulling indices from an atomic counter, each writing its own result slot (deterministic input order, independent solves). Compute-only timing, 1 warm-up, 5 repetitions, median.
System (results/benchmark_system.txt): Intel Xeon @ 2.80 GHz, 1 physical/1 logical core, 3.9 GiB RAM, GCC 13.3.0, -O2 -std=c++17. Workload 3000 cases x 4000 elements.
Result: 1 worker 0.2522 s (serial); 2 workers 0.2450 s (speedup 1.03, eff 0.51); 4 workers 0.2410 s (1.05, 0.26) - **the 2 and 4 worker runs are oversubscribed (workers > logical CPUs); they demonstrate the parallel path and that results agree (max |difference| = 0 <= 1e-8 C), but speedup cannot be assessed on this machine.** Expected behaviour on a multicore machine: near-linear scaling until memory bandwidth/allocation costs dominate (each solve allocates four vectors of n+1 doubles). Launch-to-ready (main() to listening) was 0.1 ms; wall-clock from double-click to browser paint on Windows is **not measured** [CANDIDATE: stopwatch]. A tiny workload with 2 repetitions gave a spurious 2x "speedup" on this single CPU (first-repetition cold-start noise) - a reason to use the full workload and 5 repetitions.
